Section 01

Project Overview

The Vehicle Management System (VMS) simulates a lightweight vehicle database using only basic data structures — structures and static arrays — with complete manual handling of records. It demonstrates how real-world fleet information systems work in a simplified, dependency-free environment.

🚗

Fleet Records

Store up to 100 vehicle records, each carrying 13 typed attributes with auto-generated unique IDs.

⚙️

Modular Design

Ten translation units split by responsibility, coordinated through a single shared header vehicle.h.

📊

Analytics & Billing

Five analytical reports plus a rule-based service-charge calculator covering all five vehicle types.

💡
Design Philosophy

No external database, no file I/O, no third-party libraries. Every byte of state lives in program memory and every operation is performed manually — making the code an excellent reference for structured programming, array manipulation and record-shifting algorithms.

Section 02

Objectives & Scope

What this project set out to achieve, and the boundaries it operates within.

✅ Objectives

  • Implement a complete record management system in C using structures and arrays.
  • Practice modular programming by splitting logic across focused source files.
  • Understand manual data storage: insertion, deletion, shifting, searching and traversal.
  • Enforce robust input validation with type-specific ranges and retry policies.
  • Provide analytical reporting and a deterministic billing engine.
  • Guarantee the program never terminates until the user explicitly selects Exit.

🎯 Scope Boundaries

  • In scope: In-memory CRUD, filtering, search, summary, billing, undo, cloning.
  • In scope: Command-language bulk deletion and partial (multi-record) updates.
  • Out of scope: Persistent storage (files/databases) — data is lost on exit.
  • Out of scope: Graphical user interface, networking, multi-user concurrency.
  • Out of scope: Authentication, access control or audit logging.
  • Constraint: Fixed capacity of MAX = 100 records.
📌
Problem Statement

Design and implement a Vehicle Management System that lets users store information about different types of vehicles and perform structured operations — add, list, search, update and delete — while continuing to function correctly regardless of how many operations are performed, until the user explicitly exits.

Section 06

System Architecture

A classic menu-driven control loop architecture. main() owns an infinite while(1) loop, validates the numeric choice, and dispatches to the responsible module through a switch statement. All modules share global state declared in vehicle.h and defined once in add.c / main.c.

2 Print Menu

3 Read Choice

4 Validate Input
→
5 Dispatch Module
→
6 Update State
→
↻ Loop / Exit
src/main.c — dispatch core
while (1) {
    printf("\\n=====================================\\n");
    /* ... print menu items 1-9 and 0 ... */

    if (scanf("%d", &choice) != 1) {
        printf("\\nInvalid input!\\n");
        while (getchar() != '\n');   // flush bad input
        continue;
    }

    switch (choice) {
        case 1: addVehicle();         break;
        case 2: showVehicles();       break;
        case 3: updateVehicle();      break;
        case 4: deleteVehicle();      break;
        case 5: searchVehicle();      break;
        case 6: filterVehicle();      break;
        case 7: summaryVehicle();     break;
        case 8: billingVehicle();     break;
        case 9: undoLastOperation();  break;
        case 0: return 0;            // clean exit
        default: printf("\\nInvalid choice! Please try again.\\n");
    }
}
✔
Why this shape?

A switch-dispatch loop keeps the menu, the navigation and the business logic fully decoupled — each module can be read, tested and modified in isolation.

🔗
Shared header pattern

vehicle.h uses an include guard and extern declarations so every translation unit sees exactly one copy of each global.

Section 07

Data Model

The heart of the system — a single struct Vehicle that flattens every vehicle type into one record with type-specific optional fields.

src/vehicle.h — record definition
#define MAX 100

struct Vehicle {
    char id[10];              // "V001", "V002", ... auto-generated
    char type[30];            // Bike | Car | Truck | Bus | Electric Vehicle
    char model[50];            // Model name
    char brand[50];            // Manufacturer
    int  year;                 // Manufacture year (must be >= 1999)
    int  engineCapacity;       // cc (0 for Electric Vehicle)

    char color[20];            // Common field
    char fuelType[20];         // Common field (unused by EV)

    int  seatCount;            // Car (2-12) / Bus (20-50)
    int  gearCount;            // Bike (<= 4)

    int  batteryCapacity;      // EV only, 1000-12000 kWh
    int  chargeTime;           // EV only, 1-24 hours

    char routeNumber[20];      // Truck route identifier
};

📐
Design note — the "fat struct" trade-off

All five types share one structure instead of a base struct + subtypes. This keeps array indexing trivial (vehicles[i] = vehicles[j] is a one-line copy) at the cost of unused fields per record — a deliberate, beginner-friendly simplification documented here so readers understand the trade-off.

Core Operations

The five fundamental record-management operations, with their exact behaviour and edge cases.

Insert Flow

1 Choose mode
→

→
3 Pick type
→
4 Common fields
→
5 Type fields
→
6 Commit
  • ID is generated before any input via sprintf(id,"V%03d",vehicleCounter).
  • Type is chosen from a numbered 1–5 sub-menu, never free-typed.
  • Common fields: model, brand, year (≥ 1999), then colour last.
  • On any validation abort, count is not incremented — no partial record is committed.
  • Success sets lastOperation = UNDO_ADD and undoIndex = count-1.

Clone Mode

Option 2 copies an entire existing record and stamps it with a fresh ID — a fast template for near-identical fleet entries.

  • Prompts for a source Vehicle ID.
  • Performs a struct assignment vehicles[count] = vehicles[i].
  • Overwrites the ID with the next generated value.
  • Reports "Vehicle ID not found" when the source is absent.
💡
Uniqueness guarantee

Because IDs come from a monotonically increasing counter, duplicates are structurally impossible — no scan is ever needed.

1 · Show All

Renders every record with a numbered header block and all attributes relevant to its type. Empty store prints "No vehicles available."

2 · Grouped by Type

Five fixed sections — Bikes, Cars, Buses, Trucks, EVs — each printing a compact one-line summary per record.

3 · Electric Only

Filters on type == "Electric Vehicle" and shows battery capacity and charge time; prints a notice when none exist.

Feedback

Mode 1 — Update by ID

  • Displays the current record before allowing changes.
  • Eight field choices: model, brand, year, engine capacity, colour, fuel type, type-specific value, or all fields.
  • Choice 7 auto-routes: Bike → gear count, Car/Bus → seat count, Truck → route number, EV → battery or charge time.
  • Snapshots the record into undoVehicle before writing.
  • Unknown ID prints "Vehicle not found!".

Mode 2 — Partial Update

Match by (4 options): Brand · Vehicle Type · Engine capacity greater than · Battery capacity (EV only).

Update (6 options): Brand · Type · Engine capacity · Colour · Fuel type · Battery capacity.

  • Scans the whole array once, mutating every record satisfying the predicate.
  • Ideal for renames such as Honda → Honda Motors.
  • Undo snapshot tracks only the last matched record (see §15).

Compaction algorithm

Records after the deleted slot are shifted one position left with a manual loop; count is decremented so there are never holes in the array.

🔄
Retry policy

Numeric fields use a bounded while (attempts < 2) loop. Two consecutive invalid entries print "Too many invalid attempts. Aborting vehicle addition." and the whole insert is rolled back — the ID counter has already advanced, so the skipped ID is never reused.

⌨️
Buffer safety note

String fields are read with scanf(" %[^\n]", ...) which consumes spaces but is not width-limited in the current implementation. For production use, switch to %49s-style width specifiers or fgets. This is tracked in §20.

Common Adjustments

🕐️
Age surcharge — +200 TK

Applied when currentYear − year > 5. The reference year is a compile-time constant currentYear = 2026, so any vehicle manufactured before 2021 attracts the surcharge.

🛡️
Floor value — never negative

After all tiers and surcharges, if (charge < 0) charge = 0; guarantees a non-negative payable amount under any input combination.

Computation pipeline
int charge = resolveBaseTier(vehicle);   // per-type table
if (currentYear - vehicle.year > 5)
    charge += 200;                       // age surcharge
if (charge < 0)
    charge = 0;                          // non-negative floor
printf("Service Charge      : %d TK\n", charge);
Section 15

Undo System

A single-level snapshot mechanism that reverses the most recent mutating operation.

↩ UNDO_ADD

Simply decrements count, logically discarding the record appended last. The ID counter is not rolled back, so the ID is permanently retired.

↩ UNDO_UPDATE

Restores the stored snapshot: vehicles[undoIndex] = undoVehicle. Works for both single and partial updates.

↩ UNDO_DELETE

Shifts every record from undoIndex onward one slot to the right, re-inserts the snapshot and increments count.

src/undo.c — full implementation
void undoLastOperation() {
    int i;

    if (lastOperation == UNDO_NONE) {
        printf("\nNo operation to undo.\n");
        return;
    }

    if (lastOperation == UNDO_ADD) {
        count--;
        printf("\nLast add operation undone successfully.\n");
    }
    else if (lastOperation == UNDO_UPDATE) {
        vehicles[undoIndex] = undoVehicle;
        printf("\nLast update operation undone successfully.\n");
    }
    else if (lastOperation == UNDO_DELETE) {
        for (i = count; i > undoIndex; i--)
            vehicles[i] = vehicles[i - 1];
        vehicles[undoIndex] = undoVehicle;
        count++;
        printf("\nLast delete operation undone successfully.\n");
    }

    lastOperation = UNDO_NONE;   // undo is single-shot
    undoIndex = -1;
}
⚠️
Known behaviour — partial update undo

When a condition-based update matches n records, only the last matched record is snapshotted (the loop overwrites undoVehicle each iteration). Undo therefore restores just that one record. This limitation is documented and queued in the roadmap (§21).

🎮
Depth = 1

After one undo, lastOperation resets to UNDO_NONE, so a second consecutive undo reports "No operation to undo." A full undo stack is a planned enhancement.

Complexity Notes

Asymptotic cost of each operation, where n = number of stored records (count).

OperationTimeSpaceBottleneck
Add (manual / clone)O(1)O(1)Constant work; ID from counter
Show allO(n)O(1)Single sequential pass

Update by IDO(n)O(1)Locating the record
Partial updateO(n)O(1)Single predicate pass
Delete by IDO(n)O(1)Search + left-shift of tail
Bulk deleteO(n·k)O(1)k deletions each shifting the tail

📈
Scalability outlook

At MAX = 100 every operation completes in microseconds — linear scans are entirely appropriate. If the cap were raised to 10⁵+, an ID hash map would turn search/lookup into O(1) and a linked structure would remove shift costs on deletion.

Section 20

Limitations & Known Issues

Honest assessment of the current implementation. Nothing here is hidden — each item has a matching roadmap entry.

🔴 High Impact

  • No capacity guard on add. Once count reaches 100, further inserts write past the array — a buffer overflow. Needs an if (count >= MAX) check.
  • No persistence. All data vanishes on exit; there is no file or database backing store.
  • Unbounded string scans. scanf(" %[^\n]", …) on a 20-byte field with longer input overflows the buffer.

🟠 Medium Impact

  • Partial-update undo is partial. Only the last matched record is restored (§15).
  • Undo depth of one. No operation history stack.
  • Bulk delete undo is lossy. undoVehicle retains only the final removed record.
  • Hard-coded billing year. currentYear = 2026 must be updated manually each year.

🟡 Low Impact

  • No sorting module. Sorting by year, brand or capacity is specified but not implemented.
  • No duplicate detection across model/brand/year attributes.
  • Brand report is O(n²) due to nested rescans.
  • Update choice 8 places its invalid-choice else after the EV branch, so it is unreachable.

🔵 Documentation Gaps

  • Some spec ranges in details.md differ from the code (e.g. Bus engine 1500–35000 specified vs 1500–3500 implemented, Bike 80–2000 vs 80–200). The code is the source of truth in this document.
  • EV billing formula in the spec differs from the shipped implementation; §14 documents the shipped version.
  • Dynamic array expansion (spec §4.8) is not implemented.

Section 22

Contributing & Coding Conventions

Guidelines for extending the codebase without breaking its structure.

📐 Style Conventions

  • K&R braces — opening brace on the same line as the statement.
  • snake_case for functions (addVehicle) and variables (vehicleCounter); PascalCase for the Vehicle struct.
  • All caps for macros (MAX, UNDO_ADD).
  • Every module includes "vehicle.h" — never redeclare prototypes.
  • Guard all new globals with extern in the header, define them in exactly one .c file.
  • User-facing messages are sentence case; menu banners use centred caps.
